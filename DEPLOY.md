# MailCraft deployment

This repository is deployed as a Docker Compose application. The supported
production target is a Linux VPS with Docker Engine, Compose v2, Bash, OpenSSL,
`curl`, `tar`, and `sudo` or root access. Vercel is not a supported target for
the complete application because the API requires persistent PostgreSQL,
Redis/BullMQ workers, durable sessions, migrations, and mounted encryption and
DKIM keys.

## Local development

Use Docker Desktop with the repository directory mounted. Do not install Node
dependencies on the host:

```bash
cp .env.example .env
docker compose up --build -d
docker compose exec api npm run db:validate
docker compose exec api npm test
```

Open `http://localhost:4200`. The web and API containers use polling so source
changes reload on Windows. The local database and Redis ports remain private to
the Compose network.

To stop the stack while preserving data:

```bash
docker compose stop
```

## Production on the VPS

Point the Cloudflare DNS `A` record for `app.zendix.site` to the VPS address
before requesting the certificate. Allow TCP ports 80 and 443. Keep Cloudflare
on DNS-only during the first certificate issuance; after it succeeds, use
**Full (strict)** if the record is proxied. Do not cache `/api/*`,
`/unsubscribe/*`, or `/email-view/*`.

Clone the repository on the VPS and run the deployment workflow from its root:

```bash
git clone https://github.com/martirspe/zendix.git mailcraft
cd mailcraft
bash scripts/deploy.sh --init
bash scripts/deploy.sh --check
bash scripts/deploy.sh --bootstrap-owner
```

`--init` creates `.env.production` and four persistent secret files without
printing their values. It never replaces an existing complete secret set.
`--check` validates Docker, Compose, the hostname, TLS email, ports and secret
mounts without building or changing services. The normal deploy builds the
migrate, API and web images, runs tests, starts PostgreSQL and Redis, creates a
private pre-migration backup, applies Prisma migrations, and starts the API and
web services. It then creates a separate host-Nginx virtual host and obtains a
certificate with Certbot. Existing host applications and virtual hosts are
left in place; conflicts stop the deployment for manual review.

For an existing checkout, update safely with:

```bash
bash scripts/deploy.sh --pull
```

The script requires a clean checkout and performs a fast-forward-only pull. To
validate the Docker stack without changing host Nginx or TLS, use:

```bash
bash scripts/deploy.sh --skip-host
```

That mode reports private stack health only; it does not claim public HTTPS
readiness.

## Configuration and secrets

`.env.example` contains only local development values. `.env.production.example`
contains the non-secret production settings required by Compose:

- `APP_HOST`: public console hostname, currently `app.zendix.site`.
- `ACME_EMAIL`: monitored address for certificate notices.
- `JWT_SECRET_PATH`, `VAULT_KEY_PATH`, `DATABASE_PASSWORD_PATH`, and
  `REDIS_PASSWORD_PATH`: files generated by `--init` and retained across
  deployments.
- `WEB_PORT`: loopback port used by host Nginx, default `8092`.

SMTP credentials, Cloudflare tokens, sender-domain records, and DKIM material
are configured per tenant in the console and encrypted at rest. They must not
be placed in Git or in `.env` files. The production API derives
`DATABASE_URL` and `REDIS_URL` from the mounted password files; `NODE_ENV`,
`APP_PUBLIC_URL`, registration policy, and secret-file locations are set by the
production Compose manifest.

## Post-deployment checks

Run these checks from the VPS:

```bash
docker compose --env-file .env.production -p mailcraft-production \
  -f compose.production.yaml -f compose.host-proxy.yaml ps
curl --fail https://app.zendix.site/api/health
```

Then sign in, configure MailChannels and Cloudflare from the console, verify
the sender DNS records, send the authorized preview, and confirm the received
message and unsubscribe link. Commercial bulk sending remains disabled until
provider delivery-event verification and the complete audience dispatch flow
are enabled and tested.

Keep the private `backups/pre-deploy-*` directories and move encrypted copies
off the VPS. Restore PostgreSQL, the matching secret files, and the DKIM key
volume together; never regenerate production secrets for an existing database.
